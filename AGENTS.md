# Agent guidance

These instructions apply throughout this repository.

## Workflow

1. Use the release milestone in Linear’s canaslan.com project as the source of scope. Before implementing an assigned issue, check its acceptance criteria. If any are missing or unclear, ask the user and record the agreed criteria on the issue.
2. Inspect the relevant existing code before editing. Keep changes focused and preserve unrelated user work.
3. When the milestone implementation is ready, run `npm run build` and then `npm run preview -- --port 4322`. Review the built site at [the local review URL](http://localhost:4322). Confirm the server reports that address before sharing it and keep it available for the user’s review.
4. Test each issue against its acceptance criteria and the Verification section below. Record results, verification gaps, and relevant local page links on the issue. Fix known failures and retest before moving the issue to **In Review** for user testing.
5. If the user flags a defect, record it on the issue, fix it, rebuild the local preview, and repeat the affected checks. Return it to **In Review** with the results. Only the user sets an issue to **Approved**.
6. Once the user has approved every issue in the milestone, assemble a local release commit containing only the scoped changes. Include the new version in `siteVersion` in `src/data/navigation.ts`. Build and review that commit locally, including the navigation pill. Draft the GitHub release notes and give the user the draft, candidate commit SHA, and local URL for final review.
7. Wait for the user to approve both the candidate commit and release draft. If the candidate changes, repeat the affected checks and obtain approval for the revised commit. Before pushing, record the current production version and commit as described in [the deployment guide](docs/deployment.md).
8. Push the approved commit to `main`, which triggers the Cloudflare production build. Verify the remote commit SHA and successful deployment of that SHA. Run the deployment guide’s production checks and confirm that the live navigation pill shows the candidate version.
9. Publish the approved GitHub release against the verified production commit and confirm the release tag resolves to that SHA. Record the release link and production verification results in Linear. Leave issues **Approved** as the final issue status. If deployment or verification fails, record the failure and keep the release draft open until resolved.

## Changelog and version naming

- GitHub Releases is the site’s version log. Summarise the milestone’s user-visible changes and fixes in the release notes.
- Increment from the latest published site release. Use a patch increment for fixes only (v1.1 to v1.1.1), a minor increment for a new feature or section (v1.1.1 to v1.2), and a major increment for a major redesign (v1.2 to v2.0). For mixed releases, use the highest applicable increment.

## Preserve the design system

- Preserve the Figma-defined visual language: typography, color roles, spacing, layout, icons, and interaction states. Do not introduce a new visual style unless requested.
- Reuse the Figma-exported design tokens in `src/tokens/`. Prefer semantic color aliases such as `--text-primary` and `--surface-default` over raw colors or base palette values.
- Use existing spacing, typography, icon, and viewport variables instead of adding arbitrary values when a suitable token exists. Explain any necessary new token or exception.
- `src/styles/tokens.css` and `src/styles/breakpoints.css` are generated by `scripts/generate-tokens.mjs`. Update the source tokens or generator as appropriate, then run `npm run tokens`; do not hand-edit generated files. Review generated changes for unintended differences.
- Reuse components in `src/components/`, including `Link.astro`, `InfoTable.astro`, `Breadcrumb.astro`, and the navigation components. Extend existing patterns before creating duplicates.
- Use `src/layouts/Layout.astro` for the shared page shell and global typography. Preserve the existing font families, size scale, weights, line heights, and letter spacing; inspect component styles for contextual typography before adding overrides.
- Follow `src/styles/layout.css` for the implemented responsive layout. Exported grid tokens alone do not define the active page grid. Keep media-query literals aligned with the viewport tokens and generated breakpoint reference.
- Preserve both light and dark themes, including system preference and explicit theme selection. Check affected interactive states in both themes.

## Accessibility

- Implement changes to meet applicable WCAG 2.2 Level AA requirements. Preserving the visual language does not justify an accessibility regression; explain any design adjustment needed for accessibility.
- Prefer semantic HTML: appropriate landmarks, logical heading hierarchy, links for navigation, buttons for actions, and associated labels for form controls. Use native elements before adding ARIA.
- Ensure keyboard operation, visible and unobscured focus, accessible names, and appropriate focus management for overlays. Avoid keyboard traps and restore focus when dismissing an overlay.
- Provide meaningful alternative text for informative images and hide decorative imagery from assistive technology. Do not communicate meaning through color alone.
- Check contrast, target sizes, text resizing, and responsive reflow. Respect reduced-motion preferences when adding animation.

## Astro and dependencies

- Prefer native Astro components, static rendering, semantic HTML, and CSS. Add client-side JavaScript only for behavior that requires it, keeping its scope and shipped size small.
- Follow the existing script and component patterns. Do not introduce a client framework or hydrate static content without a concrete need.
- Reuse browser APIs and existing dependencies where practical. Add a dependency only with a clear reason that explains why existing tools are insufficient and accounts for bundle size and maintenance cost.

## Verification

- Run checks relevant to the change after implementation. For application changes, run `npm run build`; its `prebuild` hook regenerates tokens automatically.
- For token changes, run `npm run tokens` and inspect the generated output. Check any affected media-query literals when changing viewport tokens.
- For UI changes, inspect affected pages at mobile and desktop sizes and in light and dark themes. Check keyboard navigation, focus, overflow, and relevant accessibility requirements. Automated checks alone do not establish WCAG conformance.
- Use existing test, lint, or type-check commands if added to the project. Currently, `package.json` does not define separate test, lint, or type-check scripts; do not claim these checks ran.
- For documentation-only changes, verify referenced paths and commands and review the diff; an application build is unnecessary unless runtime behavior is affected.
- Report what changed, which checks ran, their results, and any remaining verification gaps.
